## Context

The ERP has a design system in Figma organized with Atomic Design: tokens, atoms, molecules and organisms. It has more than 300 published components and two variable collections, one semantic and one for components, on top of the primitives.

The release I designed brought three new modules. They needed pieces the system didn't have, like an inline alert or a step wizard, and states no component covered, like a list that fits on a single page.

## Decisions and what they cost

### Each component with its own tokens

**The problem.** Several components pointed straight at the semantic colors. Changing, say, the border of the info alert meant touching the semantic color, and with it everything else that used it.

**The decision.** The chain has three links: primitive, semantic and component. Components only consume the last one. The inline alert ended up with 13 tokens of its own: background, border and icon for each of the four types, plus one text token they share. Each one is an alias of the semantic color it was already using. I derived the tokens node by node from what the design already used, so the change didn't move a pixel.

**What it costs.** There are more variables to maintain, and a component token pointing at the same semantic color as another looks redundant. That's the price of being able to change one without dragging the other along.

### One token per level of composition

**The problem.** The step wizard had 19 tokens on a single level. Even so, 24 nodes were still bound to semantic colors: the labels and connectors never had a token.

**The decision.** I reorganized it into three levels and assigned each token to the level of the node that consumes it. The circular marker kept 13, the marker with a label adds 4 for type, and the full sequence adds only the 2 for the connector. Each level contributes its own and inherits the rest.

**What it costs.** Three components instead of one. In exchange, if the connector changes color, nobody has to search 19 variables to find which one is theirs.

### States are variants

**The problem.** Pagination had no states. There was a disabled-arrow token nobody used: someone planned the state and never built it. Meanwhile, the release's lists fit on one page and showed an active "next" arrow with nowhere to go.

**The decision.** I turned pagination into a set with five states: First, Middle, Last, Single page and No results. Whoever builds the screen picks the state, with no guessing about which combination of toggles produces it. The same goes for tables: read and edit are variants of one component, not two twin components.

**What it costs.** The set grows with each state. I had to reassign by hand 63 instances that were in the wrong state.

### A defect that only shows up in one context

**The problem.** When I applied the button size rule, the footer buttons went from Medium to Large and started losing their left border. There were 55 buttons in a single module. Nothing looked wrong in the component itself.

**The decision.** I looked for the cause instead of patching each screen. Of the button's 9 bordered variants, 5 drew the border outside and 4 inside. An outside border sits beyond the node, and the screen's container clipped it three levels up. I normalized all 9 variants to draw the border inside.

**What it costs.** Nothing visible. This kind of defect only shows up when you compare the area each node takes up with the area that actually renders, so that's now one more check before closing a module.

## How I worked

- **No visual change.** I checked every token change by comparing before and after. A token change that alters a pixel was done wrong.
- **No broken instances.** Renaming a component or turning it into a set doesn't disconnect its instances, because they link by key. I checked the wizard's 78 instances and another module's 262 before calling a change done.
- **Documentation on the canvas.** Each component has its own page with a spec card and color sheets. In each row, under the token, sits the semantic color it inherits from. I found spec cards cloned from other components that described something else, and rewrote them in full.

## What I learned

I learned to use MCP servers to build and to audit. Building a component by hand is slow, but reviewing it by hand is worse: a node bound to the wrong color or a border drawn outside looks fine on the canvas. With scripts connected to Figma I could sweep hundreds of instances, find what wasn't visible, and confirm a change didn't move a pixel before publishing it.

That changed how I close work. Looking right isn't enough anymore: it has to pass the audit.
